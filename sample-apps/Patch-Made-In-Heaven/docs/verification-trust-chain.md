# Sandbox Execution and Verification Trust Chain Specification

This document details the isolated container sandbox execution framework and server-owned verification trust chain implemented in `mcp/src/services/sandbox.client.ts`, `mcp/src/services/verification-run.client.ts`, and `mcp/src/tools/submit.tool.ts`.

## Isolated Docker Sandbox Engine

The `SandboxClient` class manages isolated execution of candidate source code against target test commands.

### Image Allowlist Security

Container images are strictly resolved from a pre-defined allowlist mapping programming environments to minimal container bases:

* `python`: `python:3.11-slim`
* `javascript`, `node`, `typescript`: `node:20-slim`
* `go`: `golang:1.22-alpine`
* `docker`, `general`: `alpine:3.19`

User-supplied image strings are rejected to prevent unauthorized container execution.

### Isolation and Resource Caps

Containers are spawned via argument arrays (`execFile`) with security constraints:

* Network Isolation: `--network none` disables network interface access.
* Privilege Controls: `--cap-drop ALL` drops Linux capabilities, and `--security-opt no-new-privileges` prevents privilege escalation.
* Resource Limits: `--memory 256m`, `--cpus 1`, `--pids-limit 128`.
* Filesystem Restrictions: Container root filesystem is mounted read-only (`--read-only`). Source code directory is mounted read-only (`-v tempDir:/workspace:ro`). A temporary writeable ramdisk is provided at `/tmp` (`--tmpfs /tmp:rw,size=64m`).

### Output Bounding and Timeout Cleanup

* Output Limits: Standard output and standard error streams are capped at 65,536 bytes. Streams exceeding this cap are truncated, and a truncation flag is returned.
* Execution Timeout: Default timeout is 10,000 milliseconds. If execution exceeds this window, `SIGKILL` is sent to the container process, a forced container cleanup (`docker rm -f containerName`) is executed, and a `TIMEOUT` status is recorded.

## Server-Owned Verification Run Persistence

The `VerificationRunClient` class manages persistence of verification evidence in a secondary Elasticsearch index named `hacksmymachine-verification-runs`.

### Data Model and Cryptographic Digests

When `verify_fix` executes candidate code, it generates an immutable Verification Run record containing:

* `verificationRunId`: Unique UUID generated by the server.
* `status`: Verification outcome (`PASS`, `FAIL`, or `TIMEOUT`).
* `patchDigest`: SHA-256 hex digest computed directly from the unified diff patch text.
* `testCommand`: Executed test command.
* `environment`: Environment metadata object.
* `diff`: Unified diff patch string.
* `stdout` and `stderr`: Captured output streams.
* `exitCode`: Execution exit code (0 for pass).
* `durationMs`: Execution duration in milliseconds.
* `createdAt` and `expiresAt`: ISO timestamp strings.

### Time-To-Live Expiration

Verification Run records have a default Time-To-Live of 24 hours (86,400,000 milliseconds). Lookups attempted after expiration return `null`, invalidating stale verification evidence.

## Trust Chain Validation in submit_fix

The `submit_fix` tool enforces zero-trust indexing. It rejects caller-supplied verification flags and validates submissions against active server-owned Verification Run records through six validation gates:

1. Verification Run Existence: Looks up `verificationRunId` in `hacksmymachine-verification-runs`. Rejects submission if the record is missing or expired (`REJECTED`, code: `VERIFICATION_RUN_NOT_MATCHED`).
2. SHA-256 Patch Digest Match: Compares the submitted patch text SHA-256 digest against the stored `patchDigest` in the Verification Run record. Rejects submission on mismatch.
3. Verification Status Gate: Requires the matched Verification Run to have `status === PASS`. Rejects submission if status is `FAIL` or `TIMEOUT` (`REJECTED`, code: `VERIFICATION_NOT_PASSED`).
4. Environment Equivalence Check: Normalizes and compares package versions, language, and framework metadata between submission input and the Verification Run environment. Rejects submission on mismatch (`REJECTED`, code: `ENVIRONMENT_MISMATCH`).
5. Knowledge Card Schema Validation: Constructs a Knowledge Card record and validates it against Zod schemas. Requires `exitCode === 0`, non-negative execution duration, and non-empty log evidence (`stdout` or `stderr`). Rejects submission on schema failure (`REJECTED`, code: `SCHEMA_VALIDATION_FAILED`).
6. Trust Rule Assertion: Evaluates `isTrustedForIndexing(card)`, ensuring the record contains verified execution logs and a `PASS` status before indexing into `hacksmymachine-fixes`.
