## Gotchas I hit building W1 — save yourself the time

Full detail in `CLAUDE.md`, verified directly against
`node_modules/@nitrostack/core/dist/core/*.d.ts`, not assumed from docs:

- **`import { Tool } from '@nitrostack/core'` gets you the wrong thing.**
  `Tool`/`Resource`/`Prompt` bare are builder *classes*, not decorators. Use
  `import { ToolDecorator as Tool, ControllerDecorator as Controller } from '@nitrostack/core'`.
  This one will bite you immediately in `forge.tools.ts`.
- `@Controller(prefixOrOptions?)` — optional, but your controller class needs
  it (or equivalent) to register in DI. Bare `@Controller()` = no prefix.
- `ConfigModule`/`ConfigService` come from `@nitrostack/core`, not
  `nitrostack/config`.
- `@Injectable({ deps: [...] })` is the SDK's own recommended pattern for
  ESM — don't rely on implicit constructor-metadata injection working
  reliably. See `planner.service.ts` for the pattern.
- `@Cache` (if you use it anywhere) shares its store across instances, keyed
  by `ClassName:methodName:JSON(input)` — call `clearCache()` between test
  runs that reuse the same input.
- `nitrostack-cli` (global npm install) has no runnable `bin` in the public
  registry snapshot I hit. BUILD-W2's Phase 1A (`npx @nitrostack/cli init
  _skeleton`) may not work as written — if it doesn't for you either, you'll
  need to hand-build `templates/skeleton/` the same way I hand-scaffolded
  this whole repo (matching the structure NitroStack expects, verified
  against the real installed package rather than the CLI's generated output).
  Flag it back if you hit this so we're not each rediscovering it.
- For `verifier.service.ts`'s boot/handshake stage: I haven't built or tested
  a raw MCP stdio handshake myself, so I can't pre-verify that part for you.
  BUILD-W2 offers a hand-written `initialize` + `tools/list` JSON-RPC
  shortcut (~40 lines) as a fallback if the real handshake eats too much
  time — that's a reasonable place to cut if you're behind, per the doc.
