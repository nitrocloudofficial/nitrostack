# Seer — Complete Project Plan

**Tagline:** *Ask your data. Understand the process. See what comes next.*

The name fits: Seer examines historical data and produces a transparent estimate or classification rather than presenting an unexplained “prediction.”

## 1. Product definition

Seer is an MCP application for non-technical users who want to answer predictive questions using tabular CSV data.

Example:

> “Based on this employee dataset, what salary is expected for a developer with ten years of experience?”

Seer will:

1. Identify the selected dataset.
2. Profile its structure and quality.
3. Interpret the natural-language question.
4. Propose a supervised machine-learning plan.
5. Ask the user to approve important decisions.
6. Train and evaluate the model.
7. Compare it against a baseline.
8. Generate a prediction or classification.
9. Present metrics, graphs, warnings and a plain-language explanation.

The primary hackathon track should be **Enterprise AI & Workplace Automation**. The product automates an analysis workflow that would normally require a data analyst or ML engineer.

## 2. MVP boundaries

### Supported

* CSV datasets exposed through MCP resources.
* One target column.
* Numeric and categorical input features.
* Regression using `LinearRegression`.
* Classification using `LogisticRegression`.
* Median imputation for numeric features.
* Most-frequent imputation for categorical features.
* `StandardScaler` for numeric features.
* `OneHotEncoder` for categorical features.
* Train/test evaluation.
* Baseline comparison.
* Natural-language explanations.
* Interactive NitroStack widgets.
* Remote Python execution through a service hosted separately from NitroCloud.

### Explicitly unsupported

* User uploads.
* Databases.
* Time-series forecasting.
* Images, audio or free-text modelling.
* Unsupervised learning.
* Deep learning.
* Arbitrary Python execution.
* Hyperparameter optimisation.
* Feature engineering generated by the LLM.
* Model persistence or downloadable model files.
* Production-grade statistical guarantees.

The correct claim is:

> Seer supports eligible supervised-learning CSV datasets.

Do not claim that it can model every CSV.

## 3. Recommended limits

These should be configuration values rather than scattered constants.

| Limit                                    | Initial value |
| ---------------------------------------- | ------------: |
| CSV size                                 |          5 MB |
| Rows                                     |        20,000 |
| Columns                                  |            50 |
| Classification classes                   |          2–10 |
| Unique categories per categorical column |            50 |
| Total encoded features                   |           500 |
| Prediction rows per request              |            10 |
| Python request timeout                   |   120 seconds |
| Plan-token lifetime                      |    15 minutes |

Reject the dataset before training when it exceeds these limits.

```text

  ▼

  ├── Tool schemas and orchestration
  ├── Plan validation
  ├── Signed approval tokens
  ├── Widgets
  └── Python service client
          │

Seer ML Service
Python / FastAPI — Google Cloud Run
          │
          ├── pandas
          ├── scikit-learn
          ├── Dataset profiling
          ├── Preprocessing

```

NitroStack’s decorator architecture, dependency injection, Zod validation, resources, prompts and widgets fit this modular design. Business logic should remain in services, with MCP tools acting as thin interfaces. ([NitroStack Docs][1])

Cloud Run supports deploying FastAPI services from source or containers and provides a Mumbai region, making it suitable for the Python component. ([Google Cloud Documentation][2])

## 5. Database decision

**No database for the MVP.**

A database would add deployment and state-management work without improving the core demonstration.

Use signed, stateless plan tokens:

```text
Dataset selected
    ↓
Dataset profiled
    ↓
Validated plan generated
    ↓
Plan encoded into signed token
    ↓
User approves token
    ↓
Analysis executed
```

The signed token contains:

```text
version
datasetId
datasetHash
question
targetColumn
featureColumns
taskType
predictionRows
preprocessingPlan
splitConfiguration
issuedAt
expiresAt
```

Sign it with HMAC-SHA256 using a NitroCloud environment secret. The execution tool must verify the signature, expiration and current dataset hash.

Because there is no persistent model store, **training, evaluation and prediction happen atomically in one analysis call**. A separate reusable `predict` tool would require reliable model persistence and is deferred.

## 6. MCP interface

### Resources

#### `seer://datasets`

Returns a JSON catalogue:

```json
{
  "datasets": [
    {
      "id": "employee-compensation",
      "name": "Employee Compensation",
      "description": "Synthetic employee compensation data",
      "taskHints": ["regression"],
      "rows": 1500,
      "columns": 8
    }
  ]
}
```

#### `seer://datasets/{datasetId}`

Returns the corresponding CSV with MIME type `text/csv`.

MCP resources are URI-addressed contextual data controlled by the host application, which makes them appropriate for the fixed sample-dataset MVP. ([Model Context Protocol][3])

The model should not reason over the full CSV contents directly. It should call `profile_dataset`, which performs deterministic server-side analysis.

### Prompt

#### `seer_guided_analysis`

Purpose:

* Establish the correct tool order.
* Prevent unsupported analysis.
* Require explicit confirmation for ambiguous targets.
* Prevent the model from inventing columns.
* Require the final response to include uncertainty and limitations.

Conceptual instructions:

```text
1. Identify the requested dataset.
2. Call profile_dataset.
3. Select only columns returned by the profile.
4. Call create_analysis_plan.
5. Do not call run_analysis until the user approves.
6. Explain predictions as estimates, not guarantees.
```

### Tools

#### 1. `profile_dataset`

Input:

```text
datasetId
```

Returns:

* Dataset dimensions.
* Column names.
* Inferred data types.
* Missing-value counts.
* Exact duplicate count.
* Numeric summaries.
* Category counts.
* Target candidates.
* Identifier-column candidates.
* Constant columns.
* Unsupported columns.
* Class distributions for low-cardinality columns.
* Sample rows.
* Warnings.
* Profile-widget data.

This must inspect the complete dataset within the configured limits, not only the header and first rows.

#### 2. `create_analysis_plan`

Input:

```text
datasetId
question
targetColumn
featureColumns
taskType
predictionRows
```

The LLM interprets the user’s question and supplies structured arguments. The tool then deterministically validates them.

Validation includes:

* Every column exists.
* Target is not included as a feature.
* Target is not constant.
* Missing target rows can be handled.
* Classification target has 2–10 classes.
* Regression target is numeric.
* No unsupported feature is selected.
* Prediction rows contain all required feature values.
* One-hot feature count remains within limits.
* Dataset contains enough usable rows.
* Numeric-coded categories are not silently treated as continuous when ambiguous.

Output:

* Normalized plan.
* Proposed preprocessing.
* Rows affected.
* Warnings.
* Assumptions.
* Signed plan token.
* Plan-approval widget data.

#### 3. `run_analysis`

Input:

```text
planToken
```

Responsibilities:

1. Verify token signature and expiration.
2. Confirm the dataset has not changed.
3. Send the CSV and plan to the Python service.
4. Report execution progress.
5. Return evaluation, prediction, chart data and warnings.
6. Render the results widget.

Configure the tool with optional task support:

```text
taskSupport: optional
```

This allows asynchronous execution where the client supports MCP Tasks while preserving a synchronous fallback. NitroStack Tasks support immediate task acceptance, progress updates, result retrieval and cancellation. ([NitroStack Docs][4])

Suggested progress stages:

```text
Validating dataset
Preparing train and test sets
Fitting preprocessing pipeline
Training model
Training baseline
Evaluating models
Generating predictions
Preparing visualisations
```

        ↓

## 8. ML pipeline

### Data validation

Before splitting:

* Reject malformed CSV.
* Reject duplicate column names.
* Reject completely empty datasets.
* Reject excessive rows, columns or file size.
* Remove rows with a missing target only after disclosing the count.
* Reject a target with no variation.
* Reject all-null features.
* Exclude constant columns.
* Exclude obvious identifiers by default.
* Reject probable free-text columns.
* Reject datetime columns for the MVP.
* Calculate exact duplicate count, but do not automatically remove duplicates without approval.

### Task selection

The LLM proposes the task, but Python validates it.

Use regression when:

* The target is numeric.
* It has sufficient distinct values.
* The user asks for an amount, score, quantity or continuous estimate.

Use classification when:

* The target is categorical.
* Or it is numeric but represents a small set of labels such as `0/1`.

Ambiguous cases must be shown in the approval widget.

### Splitting

Recommended default:

```text
80% training
20% testing
random_state = 42
```

For classification, use stratification when every class has enough samples.

All learned preprocessing must be fitted only on training data. Scikit-learn recommends splitting before fitting preprocessors and using a pipeline to prevent test-data leakage. ([Scikit-learn][5])

### Preprocessing

```text
Numeric features
    MedianImputer
    → StandardScaler

Categorical features
    MostFrequentImputer
    → OneHotEncoder(handle_unknown="ignore")

Combined using ColumnTransformer
    → Estimator
```

`ColumnTransformer` and `Pipeline` are designed for mixed datasets where numeric features require scaling and categorical features require one-hot encoding. ([Scikit-learn][6])

### Models

Regression:

```text
LinearRegression
```

Classification:

```text
LogisticRegression
max_iter configured high enough for convergence
```

### Baselines

Regression:

```text
DummyRegressor(strategy="mean")
```

Classification:

```text
DummyClassifier(strategy="most_frequent")
```

Dummy estimators deliberately ignore useful feature relationships and provide a simple reference against which the actual model can be evaluated. ([Scikit-learn][7])

## 9. Metrics

### Regression

Return:

* MAE
* RMSE
* R²
* Baseline MAE
* Baseline RMSE
* Baseline R²
* Absolute and percentage improvement over baseline

Interpretation rules:

* MAE should be explained in the target’s unit.
* RMSE should be described as more sensitive to large errors.
* Negative R² should explicitly state that the model performed worse than predicting the training mean.

### Classification

Return:

* Accuracy
* Precision
* Recall
* F1
* Per-class metrics
* Confusion matrix
* Baseline metrics
* Class distribution
* Model improvement over baseline

Use weighted metrics for the headline display and retain per-class metrics in an expandable section. Scikit-learn provides these regression and classification evaluation metrics, including confusion matrices and classification reports. ([Scikit-learn][8])

### Quality decision

The result must be labelled:

* **Useful signal:** model clearly outperforms baseline.
* **Weak signal:** improvement is small or unstable.
* **No demonstrated signal:** model does not outperform baseline.
* **Invalid analysis:** dataset or split cannot support evaluation.

Seer must still return poor results honestly. It must not hide weak model performance.

## 10. Prediction safeguards

For every prediction, return:

* Predicted value or class.
* Predicted probability for classification.
* Model evaluation summary.
* Baseline comparison.
* Input values used.
* Warnings.
* Dataset coverage information.

Generate warnings when:

* A numeric input lies outside the training range.
* A categorical value was unseen during training.
* The dataset is small.
* A class is heavily underrepresented.
* The model fails to beat the baseline.
* The prediction is extrapolation.
* Important explanatory variables may be missing.
* The dataset contains historical or biased observations.

Never phrase the result as guaranteed.

Use:

> “The model estimates…”

Not:

> “You will receive…”

## 11. Graphs and widget data

Python should return plot-ready JSON. React widgets should render the graphs.

Do not return base64 images unless necessary.

### Dataset profile widget

Show:

* Dataset dimensions.
* Column-type table.
* Missing-value bar chart.
* Target distribution.
* Numeric distributions.
* Category frequencies.
* Duplicate count.
* Data-quality warnings.

### Plan approval widget

Show:

* User question.
* Selected target.
* Selected features.
* Regression or classification.
* Preprocessing by column.
* Rows excluded because the target is missing.
* Columns excluded and why.
* Prediction inputs.
* Assumptions.
* Warnings.
* Approve and reject controls.

The approval action should trigger the follow-up `run_analysis` call. NitroStack’s richer TypeScript template explicitly demonstrates widgets and follow-up tool calls, making it the best scaffold to inspect for this interaction. 

### Results widget

Regression:

* Predicted value.
* Model-versus-baseline metric cards.
* Actual-versus-predicted scatter plot.
* Residual-versus-predicted scatter plot.
* Prediction-input coverage.
* Warnings and limitations.

Classification:

* Predicted class and probability.
* Model-versus-baseline cards.
* Confusion matrix.
* Class-distribution chart.
* Per-class metrics.
* Warnings and limitations.

Actual-versus-predicted and residual-versus-predicted are standard regression diagnostics supported by scikit-learn’s prediction-error display. ([Scikit-learn][9])

## 15. Sample datasets

Use synthetic or clearly redistributable datasets.

Recommended set:

1. **Employee compensation — regression**

   * Numeric and categorical features.
   * Some missing feature values.
   * Demonstrates salary-like prediction.

2. **Customer churn — classification**

   * Binary target.
   * Mixed features.
   * Mild class imbalance.

3. **Student performance — regression or classification**

   * Useful for demonstrating that Seer is domain-independent.

The main demonstration dataset should contain both numeric and categorical features so that imputation, scaling and one-hot encoding are visible.

Do not use sensitive real personal data.

## 16. Security

For the MVP:

* Store the Python service URL and shared secret in NitroCloud environment variables.
* Send the secret through an authorization header.
* Reject requests without the correct secret.
* Compare secrets using constant-time comparison.
* Use HTTPS only.
* Never log CSV contents.
* Never log raw prediction rows.
* Log dataset ID, dimensions, duration and correlation ID.
* Allow only known dataset IDs.
* Do not accept filesystem paths or arbitrary URLs.
* Enforce request-size limits in both services.
* Set explicit outbound timeouts.
* Return generic client errors and retain technical details in server logs.
* Do not return serialized Python models.

A shared API secret is acceptable for the hackathon. Production would require stronger service identity or OAuth-based controls.

## 19. Main risks

### NitroCloud cannot reach Cloud Run

Mitigation:

* Test this first.
* Use a public Cloud Run endpoint protected by the shared secret.
* Avoid Cloud Run IAM authentication unless NitroCloud can issue Google identity tokens.

### Dataset files disappear during NitroCloud build

Mitigation:

* Put datasets inside the source tree.
* Explicitly copy them during build.
* Add an integration test that reads them from the production build.
* Confirm the deployed resource before continuing.

### Widget approval cannot trigger a follow-up call

Mitigation:

* Test with the richer NitroStack template early.
* Fallback: the widget presents the plan and instructs the user to reply “approve”; the model then calls `run_analysis`.

### MCP Task support differs by client

Mitigation:

* Use `taskSupport: optional`.
* Keep the dataset limits low enough for synchronous execution.
* Implement the same result contract for sync and task modes.

### One-hot encoding causes feature explosion

Mitigation:

* Cardinality limits.
* Encoded-feature limits.
* Explicit rejection message.
* No automatic hashing or target encoding in the MVP.

### Model performs badly

Mitigation:

* Treat weak performance as a valid result.
* Show baseline comparison.
* Explain that the dataset may not contain sufficient predictive information.


## 20. Definition of done

Seer’s MVP is complete when all of the following work from the deployed environment:

* At least one regression and one classification CSV are exposed as MCP resources.
* A natural-language question causes the correct dataset to be profiled.
* The LLM creates a valid structured plan.
* The user sees and approves the plan.
* NitroCloud calls the Python service.
* Python preprocesses without leakage.
* The real model and baseline are trained.
* Required metrics are returned.
* A prediction or classification is produced.
* At least two meaningful graphs are rendered.
* Weak performance and extrapolation are disclosed.
* Invalid datasets fail with understandable errors.
* The complete path works through ChatGPT or the required judging client.
* The repository is public, documented and deployable.
* The final NitroCloud deployment is live.
